# AEGIS — Remediation Safety & Governance (Rule 14)

## 1. Rule 14 Mandate
In automated cloud security, reckless automated remediations (e.g. blindly deleting security groups or revoking credentials) frequently cause catastrophic production outages.

**RULE 14** governs all AEGIS remediation operations:
> *"Proposed remediations must be minimal, compatible, and accompanied by rollback instructions and verification tests. The agent must never mutate state or execute changes directly."*

---

## 2. The Four Pillars of a Compliant Remediation Proposal
Every remediation patch generated by `services/remediation_planner/patch_generator.py` must contain:

```
+-------------------------------------------------------------------------+
|                  PILLAR 1: MINIMAL COMPATIBLE DIFF                      |
|  - Precision Terraform snippet targeting only the misconfigured field.  |
|  - Idempotent AWS CLI repair command preview.                           |
+-------------------------------------------------------------------------+
                                    |
                                    v
+-------------------------------------------------------------------------+
|                  PILLAR 2: DETERMINISTIC ROLLBACK PLAN                  |
|  - Exact reverse CLI command or state reversion procedure.             |
|  - Documented break-glass recovery timeline.                            |
+-------------------------------------------------------------------------+
                                    |
                                    v
+-------------------------------------------------------------------------+
|                 PILLAR 3: EXPECTED BLAST RADIUS & IMPACT                |
|  - Enumeration of all workloads dependent on the target resource.      |
|  - Risk classification of potential service interruption.               |
+-------------------------------------------------------------------------+
                                    |
                                    v
+-------------------------------------------------------------------------+
|               PILLAR 4: VERIFICATION & REGRESSION CHECKLIST             |
|  - Explicit steps to verify resolution of the security finding.         |
|  - Functional tests confirming dependent applications remain online.    |
+-------------------------------------------------------------------------+
```

## 3. Real Example: Remediation for Public SSH Exposure (`SEC-NET-01`)

### 1. Minimal Terraform Diff
```hcl
# Replace 0.0.0.0/0 wildcard with corporate CIDR
resource "aws_security_group_rule" "restricted_management_ingress" {
  type              = "ingress"
  from_port         = 22
  to_port           = 22
  protocol          = "tcp"
  cidr_blocks       = ["198.51.100.0/24"] # Corporate VPN egress only
  security_group_id = "sg-bastion-public"
  description       = "Compliant administrative access restricted to corporate IP range"
}
```

### 2. Single-Line AWS CLI Command Preview
```bash
aws ec2 revoke-security-group-ingress --group-id sg-bastion-public --protocol tcp --port 22 --cidr 0.0.0.0/0
aws ec2 authorize-security-group-ingress --group-id sg-bastion-public --protocol tcp --port 22 --cidr 198.51.100.0/24
```

### 3. Emergency Rollback Plan
```bash
# Execute within break-glass window only:
aws ec2 authorize-security-group-ingress --group-id sg-bastion-public --protocol tcp --port 22 --cidr 0.0.0.0/0
```

### 4. Verification Checklist
- [ ] 1. Run `nmap -Pn -p 22 <public_ip>` from external network; verify port 22 reports `filtered` or `closed`.
- [ ] 2. Confirm SSH connectivity succeeds when initiated through authorized corporate VPN (`198.51.100.0/24`).
- [ ] 3. Verify VPC Flow Logs show zero ACCEPT packets on port 22 from non-corporate origins.
